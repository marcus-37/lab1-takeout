# 实验三 大模型辅助开发记录

> 记录规则：按实际发生顺序追加；只记录真实发生的事，包括模型出错与我返工的过程，
> 不事后美化。每条包含四要素：交给模型的任务、模型的产出、我发现的问题、我的处理。
> 工具：ZCode（CLI Agent），模型 GLM-5.3。

## 0. 选型与计划（2026-11-08）

- **任务**：把实验三题目、实验一的 `requirements.md`（27 条需求）、实验二的 8 张 UML
  源码与 HANDOFF 交给模型，要求给出实现计划，并列出需要我拍板的决策点。
- **模型产出**：一份 14 步实施计划（脚手架 → 模型 → 存根+规约 → 实现 → UI → 测试 →
  风格 → 回改设计 → 报告管线 → 打包），并把架构决策收敛为三个问题：GUI 框架、
  持久化方式、大模型工作流。
- **我的判断**：三个决策分别选了 PySide6、SQLite、存根+规约先行。理由：PySide6 能
  复刻实验二 UI 稿且截图效果好；SQLite 重启不丢数据、仓储层可隔离测试；存根+规约
  是题目建议的路径，也让我能在写实现前先审接口契约。
- **模型的问题**：它最初把「每步都暂停等人工审查」写进计划，14 步暂停 14 次不现实。
  我改为只在两个关键点暂停：存根+规约审查（架构契约）与代码冻结审查。

## 1. 环境与脚手架（2026-11-08）

- **任务**：建 venv、装依赖（PySide6/pylint/pytest，清华镜像）、生成包骨架、
  pylint 配置、README、AI 记录。
- **模型产出**：全部脚手架文件；`.pylintrc` 只禁用 4 项并逐项写明理由，
  其余检查保留，复杂度阈值适度放宽。
- **我发现的问题**：模型直接手写 `.pylintrc`，但本机装的是 pylint 4.1，
  配置节名与旧版不同（如 `[MASTER]` 已改名）。手写的配置可能静默失效。
- **我的处理**：要求模型先 `pylint --generate-rcfile` 生成参考配置、核对节名与
  选项名之后再写自定义配置。这个细节让我确认了一件事：模型给的配置文件必须
  验证过再采用，和代码一样。

## 2. 领域模型与仓储层（2026-11-08）

- **任务**：把实验二类图六个包逐一映射为 Python 模块（枚举/账号/店铺菜品/
  购物车订单/支付退款/配送/审计），再写 SQLite 仓储层。
- **模型产出**：models 7 个文件 + repositories 6 个文件；状态机迁移表
  LEGAL_TRANSITIONS 以实验二状态图为权威逐条登记；金额工具用纯整数运算。
- **我发现的问题**：①冒烟测试发现 money.py 忘了导入自己引用的
  ValidationError——pylint 的 E0602 当场抓住，说明「模型写完必须立即跑检查」
  不能攒批；②四类角色账号还原时全部按 Customer 构造，根因是子类没有重设
  role 默认值，构造 Rider 得到的 role 仍是 CUSTOMER——这是模型把「继承」
  理解成「复制字段」的典型疏漏，单测用四角色全链路才暴露。
- **我的处理**：①要求每写完一层立即 pylint + 冒烟再提交；②在四个子类显式
  重设 role 字段默认值，并把「子类构造即携带正确角色」写进模型层约定。

## 3. 应用服务层与端到端验收（2026-11-08）

- **任务**：按组件图实现网关 + 八个领域服务 + 时钟 + 调度器 + 种子数据，
  用脚本按需求编号逐条验收。
- **模型产出**：services 12 个文件、seed、app 装配；端到端脚本 32 项断言，
  含 200 并发抢 10 份库存（REQ-023）。
- **我发现的问题**（按发现顺序）：
  ①我把仓储层排到了服务存根之前（存根的类型标注依赖仓储类型），实际顺序
  与计划不同，如实记录；
  ②模型写的 `DeliveryTask._transit` 只做合法性校验、从不赋值 status，
  骑手接单后任务永远停在「待分配」——与订单的 `transit_to` 对照才看出来，
  静态检查发现不了（类型正确、逻辑缺失）；
  ③已部分退款的订单再整单取消会超额退款：申请金额应取「实付-已退」的
  剩余额度，这是需求没写明、实现时必须补的口径；
  ④服务变异方法最初接收调用方传来的 Order 实体，实体可能是陈旧快照，
  覆盖了数据库里的新状态——重构为「按 order_id 现取最新实体再迁移」；
  ⑤同一令牌重复提交在购物车已清空后必然指纹失配——修正幂等语义为
  「购物车为空视为重试返回首单，内容变化才要求换令牌」。
- **我的处理**：②③④⑤全部修入代码并补进验收断言；④的重构波及四个服务
  全部调用点，逐个核对。这一轮让我体会最深的是：模型的单点代码质量不差，
  但「状态存在数据库、内存对象会过期」这类跨模块一致性，它不会主动考虑，
  必须由设计者立成规矩。

## 5. PySide6 界面（2026-11-08）

- **任务**：按实验二 11 屏 UI 稿实现四角色桌面端（QSS 复刻橙色视觉），
  QTimer 心跳驱动调度器与刷新。
- **模型产出**：theme + login + 四个角色视图 + 主壳，共 7 个文件。
- **我发现的问题**：①模型给 `.pylintrc` 加了 Qt 信号豁免后，我抽查发现它把
  一个退款列存成了「布局」而其余三列存「字典」，两种类型混用，刷新时崩溃——
  离屏冒烟测试（QT_QPA_PLATFORM=offscreen）当场暴露，说明界面代码同样
  必须有自动化冒烟，不能靠肉眼；②sed 批量改名后有两处引用没跟上，
  靠 pylint 的 E0602 兜住。
- **我的处理**：统一四列的数据结构；把「每层写完立即 lint + 冒烟」固化为
  流程；界面禁用 broad-exception 的理由写进模块 docstring。

## 6. pytest 套件与测试驱动修复（2026-11-08）

- **任务**：把手写验收脚本收编为 pytest 套件（领域单元 + 调度 + 并发 + 集成）。
- **模型产出**：6 个测试文件 63 个用例。
- **我发现的问题**：写测试反过来暴露了两个服务层缺陷——骑手完成单统计
  走了「未完任务」查询导致永远为 0；营业额把未支付订单也计了进去（口径错）。
  另有一处测试用例自身设计错：想测令牌重放却生成了新令牌，等于没测。
- **我的处理**：修服务（新增历史任务查询、营业额只计已支付），重写测试并
  补上「旧令牌 + 已取消订单不复活」「同菜品多行预占失败整单回滚」两条
  REQ-024/005 的边界。结论：测试不是写完就完，跑红→修服务→跑绿的循环
  才是测试的价值所在；而「测试通过」不等于「测试测到了」——重放用例
  第一次就是假通过，是我读了断言语义才发现的。
- 最终：pytest 63 通过、pylint 10.00/10、端到端 32 项全过、全库 6939 行。

## 7. 报告截图阶段（2026-11-12）

- **任务**：为报告"编译与运行结果"章节生成五张界面截图，写 `scripts/take_shots.py`
  离屏摆放真实数据（待接单/制作中卡片、待派送队列）后抓帧。
- **模型产出**：截图脚本一版跑通四张，第五张报错。
- **我发现的问题**（脚本过程连环暴露两个真缺陷）：
  ①确认订单对话框给范围外楼栋禁选时调用了 `QModelIndex.setEnabled`——这个
  方法不存在，真实用户打开对话框就会崩溃。此前所有冒烟都没打开过这个
  对话框，是"测试覆盖了服务层、没覆盖对话框构造"的盲区；修复改用
  QStandardItemModel 的 QStandardItem.setEnabled。
  ②截图里商家/管理端出现新旧卡片文字重叠——`_clear_layout` 只调
  deleteLater，延迟删除要等事件循环，抓帧时旧控件还画在原地。修复是
  清布局时先 setParent(None) 立即脱离绘制树（四个视图统一改）。
- **我的处理**：两处都修入产品代码而非只在截图脚本里绕过——①是会崩的
  用户可见 bug，②是真实应用快速刷新时也会闪的隐患。教训：离屏冒烟只点
  了视图刷新，没点开过对话框，下一轮把"每个对话框至少构造一次"补进
  冒烟范围；截图脚本 take_shots.py 从此留在 scripts/ 里，作为可复现的
  报告配图工具。
